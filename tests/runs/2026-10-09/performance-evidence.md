# 玻璃面板与性能：证据审查

目前不能认定玻璃面板导致应用变慢。它可以是待验证的候选因素；“看起来像玻璃”既不能证明实现用了实时模糊，也不能证明它是性能瓶颈。

本次仅收到“截图有玻璃面板”的文字描述，没有实际图片、代码、可运行应用或性能记录。因此没有检查面板的数量、面积、样式或动态行为，也没有复现“慢”。用户的目标是判断是否应为了性能修改这些面板；具体慢在加载、滚动、点击响应还是任务完成，尚不清楚。

| 项目 | 证据性质 | 当前判断 |
| --- | --- | --- |
| 界面存在玻璃面板 | 用户描述，未见图片 | 只能记录这一描述，不能推断 CSS 或渲染方式 |
| 应用运行缓慢 | 用户报告，未复现 | 症状、设备和触发操作未确定 |
| 面板导致缓慢 | 假设 | 因果关系未建立，不能列为已确认缺陷 |

对应技能中的 AP046（视觉效果的性能成本需要测量）与 AP052（不能把静态外观当作运行证据）。该假设的置信度低，修复优先级暂不确定；先诊断比直接删除样式更有依据。玻璃效果也可能提供层级或品牌价值，在性能可接受时可以保留。

建议采用一次能区分原因的对照验证：

1. 固定设备、浏览器、数据、网络与操作路径，先复现用户所说的慢，分别记录加载、滚动、输入或点击，以及需要等待结果的任务。
2. 检查实际实现。若使用模糊或其他玻璃效果，做一个临时开关，只关闭相关效果，用普通背景维持面板布局和内容；不要同时删除组件、动画或业务逻辑。
3. 在相同条件下重复记录开关前后的 Performance trace，对比相关操作耗时、帧表现，以及脚本、布局和绘制活动。Chrome DevTools 的 Performance 面板可用于运行时性能分析。[官方工具文档](https://developer.chrome.com/docs/devtools/performance)
4. 如果关闭效果后稳定改善了同一症状，且记录支持相关渲染工作减少，才把这些效果列为性能贡献因素，再逐项缩小修改范围。若没有明显改善，继续检查记录中显示的其他瓶颈。

加载、响应、视觉稳定和流畅度是不同问题；一次实验室测量也不能代表全部真实用户。应使用与所报告症状匹配的指标，并把实验条件与真实使用数据分别说明。[Google 用户中心性能指标指导](https://web.dev/articles/user-centric-performance-metrics)

本次完成的是证据边界审查与验证方案，没有执行性能测试、修改应用或确认性能改善。现阶段不建议仅凭玻璃外观重做界面。
